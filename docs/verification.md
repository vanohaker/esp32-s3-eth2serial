Начальная загрузка страницы в Chromium заняла 2,19 с с ожиданием `networkidle`,
включая TLS и ресурсы. Это одиночное измерение на данном стенде, не оценка под нагрузкой.
Telnet оставлен выключенным, VLAN — 0, serial — 115200 8N1, SMTP — выключен.

Дамп до прошивки: `~/.local/share/esp32_eth2serial_knife/bringup-20261011/before-first-flash.bin`,
права файла 0600, каталога 0700. SHA256:

```text
c145a8ed3533081c9e1e420e644334dff5416095468a98a83dd5e0cd65a73a86
```

Старая NVS находилась по адресу `0x390000`, новая — `0x9000` размером `0x30000`.
Новая область пересекалась с данными старой прошивки и была инициализирована после
сохранения дампа. Первоначальный пароль появился до открытия USB-монитора и не был
сохранён. Первичная настройка завершена записью новой конфигурации NVS с новым
случайным паролем через официальный генератор ESP-IDF; SSH/HTTPS-идентичности
созданы самим устройством. Пароль и журналы сохранены вне репозитория в закрытом
локальном каталоге; в документации секретов нет. Это не процедура обновления:
при следующих прошивках существующую NVS сохранять.

Во время одной проверки SSH открытие Windows USB-монитора вызвало аппаратный
`USB_UART_CHIP_RESET`, из-за чего авторизация завершилась тайм-аутом. Повторные входы
без открытия COM-порта успешны; ошибки прошивки этим тайм-аутом не подтверждены.

Не проверены на оборудовании: реальный обмен UART/MAX3232 и TTL loopback,
SSH по публичным ключам и остальные сценарии отказа авторизации/каналов, Telnet,
статика/VLAN, обрыв и возврат Ethernet, microSD и X/YMODEM, SMTP, BOOT-сброс,
отключение питания и PoE, длительная нагрузка, запас стеков задач и задержки криптографии.
Проверка эксклюзивности выше относится к двум SSH-подключениям; SSH+Telnet и
конфликты с передачей файла требуют отдельного испытания по [плану](bringup.md).

## Исправление сертификата Chrome, 2026-10-11

Пользователь сообщил `net::ERR_CERT_INVALID`. Ошибка воспроизведена в Chromium
с включённой проверкой TLS. На первом аппаратном испытании браузер использовал
`ignore_https_errors=True`: это подтверждало работу интерфейса и обработчиков,
но скрыло дефект сертификата.

Сертификат первоначального генератора имел X.509 v3 с явно присутствующим пустым
блоком Extensions (`a3 02 30 00`). Mbed TLS и OpenSSL принимали такую структуру,
а [проверка BoringSSL](https://github.com/google/boringssl/blob/main/pki/parse_certificate.cc)
отклоняла её: [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280#section-4.1)
требует хотя бы одно расширение, если блок присутствует. Также отсутствовал SAN.

В `main/config.cpp` добавлены Basic Constraints `CA:FALSE`, Key Usage
`digitalSignature`, Extended Key Usage `serverAuth` и DNS SAN с hostname.
IP SAN добавляется только при статическом режиме на момент генерации; вымышленный
DHCP-адрес в сертификат не включается. Существующий дефектный сертификат
распознаётся по исходному профилю и заменяется с сохранением приватного ключа.
Корректные импортированные сертификаты под такую миграцию не попадают. Повторный
импорт сертификата с пустым Extensions отклоняется до записи NVS.

Перед обновлением сохранены текущая NVS (192 КиБ), прежний образ приложения,
публичный сертификат и снимок настроек в закрытом каталоге
`~/.local/share/esp32_eth2serial_knife/bringup-20261011/tls-fix/`.
На той же плате COM3 проверены chip/MAC и flash, затем записано только приложение
по адресу `0x40000`. NVS, таблица разделов и загрузчик не стирались.

Исправленный образ: **960 032 байта**, ESP-IDF 5.5.5. SHA256:

```text
4ce64a4e4df423b7e7cd40eea48f74ec439788968fcf10e752393e3477cf467c
```

| Проверка | Результат |
| --- | --- |
| `bash tools/build.sh` | Компиляция и линковка успешны |
| `bash tools/test.sh` | Core под ASan/UBSan и синтаксис JS — успешно |
| Запись приложения | esptool подтвердил хеш |
| Миграция на плате | Сертификат изменился, его публичный ключ сохранился |
| `tests/tls_smoke.py` | SAN и назначение сервера проверены; Chromium без `ignore_https_errors` показывает обычный `ERR_CERT_AUTHORITY_INVALID` с доступным переходом; интерфейс и API открываются |
| Вход в реальном Chromium | После явного перехода через предупреждение вход с прежним паролем успешен; настройки и пользователи совпали со снимком до прошивки |
| Некорректный импорт | Повторная отправка прежнего публичного сертификата в TLS API отклонена с указанием пустого Extensions |
| Перезагрузка через веб | Новый boot ID, повторный вход успешен; исправленный сертификат, настройки, пользователи и SSH host key сохранились |
| SSH после обновления | Вход по прежнему паролю успешен; данные в serial не отправлялись |

Заводская самоподпись по-прежнему не является доверенной для браузера. Для строгого
доверия при подключении по IP нужен свой доверенный сертификат с соответствующим
IP SAN. Исправление убирает некорректную структуру, а не устанавливает доверие в ОС.

## Заводские данные входа без USB-пароля, 2026-10-11

По указанию пользователя первый запуск без сохранённой конфигурации теперь создаёт
`admin` / `admin`. Генерация случайного начального пароля и его вывод в USB удалены.
Случайная соль и хранение PBKDF2-хеша сохранены. При наличии конфигурации загружаются
её пользователи: новая прошивка не заменяет действующий пароль заводским.
После заводского сброса следующий запуск использует ту же ветку пустой конфигурации.
README, план испытаний и описание сброса в веб-интерфейсе приведены в соответствие.

Сборка ESP-IDF 5.5.5 и `tools/test.sh` прошли. Браузерный тест с подменой API
`tests/web_smoke.py` также прошёл. В собранном образе отсутствует строка прежнего
вывода `INITIAL ADMIN PASSWORD`. Новый образ — **960 016 байт**, SHA256:

```text
73220e54431bfda19799e86d68825c3abdec17f08d62c41ba4846848ae3ca122
```

На COM3 повторно проверена идентичность ESP32-S3 и flash. Текущая NVS и прежний
образ сохранены в закрытом каталоге
`~/.local/share/esp32_eth2serial_knife/bringup-20261011/default-login/`.
Записано только приложение по адресу `0x40000`, хеш подтверждён esptool.
После запуска проверены вход HTTPS и SSH с прежним сохранённым паролем,
совпадение настроек/пользователей, сертификата HTTPS и ключа SSH-сервера.
Аппаратный `tests/tls_smoke.py` с проверкой сертификатов Chromium прошёл.

Физический заводской сброс и вход с пустой NVS в этом испытании не выполнялись:
сохранена текущая конфигурация пользователя. Эти сценарии проверены по пути
инициализации в коде и остаются пунктами аппаратного плана. Данные в UART
не отправлялись.
