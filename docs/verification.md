## Исправление сертификата Chrome, 2026-10-11

Пользователь сообщил `net::ERR_CERT_INVALID`. Ошибка воспроизведена в Chromium
с включённой проверкой TLS. На первом аппаратном испытании браузер использовал
`ignore_https_errors=True`: это подтверждало работу интерфейса и обработчиков,
но скрыло дефект сертификата.

Сертификат первоначального генератора имел X.509 v3 с явно присутствующим пустым
блоком Extensions (`a3 02 30 00`). Mbed TLS и OpenSSL принимали такую структуру,
а [проверка BoringSSL](https://github.com/google/boringssl/blob/main/pki/parse_certificate.cc)
отклоняла её: [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280#section-4.1)
требует хотя бы одно расширение, если блок присутствует. Также отсутствовал SAN.

В `main/config.cpp` добавлены Basic Constraints `CA:FALSE`, Key Usage
`digitalSignature`, Extended Key Usage `serverAuth` и DNS SAN с hostname.
IP SAN добавляется только при статическом режиме на момент генерации; вымышленный
DHCP-адрес в сертификат не включается. Существующий дефектный сертификат
распознаётся по исходному профилю и заменяется с сохранением приватного ключа.
Корректные импортированные сертификаты под такую миграцию не попадают. Повторный
импорт сертификата с пустым Extensions отклоняется до записи NVS.

Перед обновлением сохранены текущая NVS (192 КиБ), прежний образ приложения,
публичный сертификат и снимок настроек в закрытом каталоге
`~/.local/share/esp32_eth2serial_knife/bringup-20261011/tls-fix/`.
На той же плате COM3 проверены chip/MAC и flash, затем записано только приложение
по адресу `0x40000`. NVS, таблица разделов и загрузчик не стирались.

Исправленный образ: **960 032 байта**, ESP-IDF 5.5.5. SHA256:

```text
4ce64a4e4df423b7e7cd40eea48f74ec439788968fcf10e752393e3477cf467c
```

## Неизменяемый HTTPS-сертификат в образе, 2026-10-11

По новому требованию пользователя удалены форма импорта, JavaScript-обработчик,
`/api/tls`, запись сертификата в NVS и его генерация на плате. HTTPS использует
PEM-сертификат и ключ из read-only данных приложения. Старая TLS-пара в NVS
игнорируется и оставлена для отката; пользователей, настройки и SSH-ключ не меняли.

Сборка подготавливает пару один раз в игнорируемом `.tls/`, проверяет её и повторно
использует. Приватный ключ не входит в отслеживаемые файлы; проверены исключение
Git и права 0700/0600. Профиль EC P-256/SHA-256 содержит Basic Constraints, KU, EKU
и DNS SAN `serial-dongle`, что исключает прежний дефект пустых расширений.
Срок текущего сертификата: 2026-10-11 — 2046-10-06.

В процессе аппаратной проверки выявлена гонка первоначальной загрузки страницы:
форма входа уже видна, а deferred JavaScript ещё не назначил обработчик.
Ранний вход выполнял стандартный GET с полями формы и получал `Not found`.
Теперь кнопка входа недоступна до установки обработчиков; резервный метод формы —
POST. Браузерный тест намеренно задерживает `/app.js`, нажимает Enter и подтверждает
отсутствие отправки до готовности интерфейса. Данные формы в отчёте не сохраняются.

Окончательный образ **952 768 байт**, версия `main-25864e1-dirty`, SHA256:

```text
e4f9b8c67b98377d7cb8464148595125405d192dcd3a7ad5665bebb65d4711bc
```

Образ записан в `0x40000` после проверки экземпляра ESP32-S3 и flash 16 МиБ.
NVS не стиралась. Резервная NVS 192 КиБ, прежний образ, снимок конфигурации и логи
сохранены в `~/.local/share/esp32_eth2serial_knife/bringup-20261011/fixed-tls/`.

Локально прошли сборка ESP-IDF, core ASan/UBSan, шесть проверок версии,
четыре проверки TLS-пары и обновлённый Chromium smoke с подменой API.
TLS-тесты проверяют настоящий локальный handshake с доверием только точному
сертификату, сохранение пары при повторной подготовке, отказ без замены файлов
при неполной или несоответствующей паре. Повторные сборки не изменили сертификат.

На устройстве сертификат побайтово совпал с `.tls/https_cert.pem` и отличается
от прежней изменяемой TLS-пары. Авторизованные GET/POST `/api/tls` возвращают 404;
прямых HTTP-маршрутов к PEM-файлам нет. Форма импорта отсутствует.

Реальный Chromium подтвердил вход и перезагрузку из веба с новым boot ID.
После перезагрузки сертификат совпал с исходным встроенным, настройки и пользователи
сохранились; SSH-вход успешен, ключ SSH-сервера прежний. Отдельный
`tests/tls_smoke.py --expected-cert .tls/https_cert.pem` прошёл: проверены точный
сертификат, DNS SAN, назначение сервера и штатное предупреждение о самоподписи
в Chromium без отключения проверки TLS.

Заводской сброс в этом испытании не выполнялся, чтобы сохранить настройки:
неизменность встроенного сертификата при сбросе подтверждается устройством кода
(сброс стирает NVS, сертификат находится в приложении).
Serial остаётся неподключённым; передачи данных и форматирования microSD не было.
