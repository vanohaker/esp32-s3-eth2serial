# Подписанные обновления прошивки через веб

В «Системе» можно загрузить **`build/eth2serial.bin`**, подписанный ключом проекта.
Это приложение для самого донгла; файлы для оборудования на serial по-прежнему
загружаются отдельно в «Файлах». microSD для обновления донгла не нужна.

1. Войти в веб как включённый пользователь. Все пользователи имеют права администратора.
2. Закрыть SSH/Telnet-сессию, дождаться окончания операций с microSD и настройками.
3. Выбрать подписанный `.bin`, нажать «Загрузить и обновить» и подтвердить перезагрузку.
4. Дождаться проверки подписи, перезагрузки и подтверждения запуска. Затем обновить
   страницу и войти снова. Настройки, пользователи и файлы microSD сохраняются.

Лимит файла — 4 МиБ, размер одного OTA-раздела, включая подпись и выравнивание.
Не загружать `eth2serial-unsigned.bin`, загрузчик, таблицу разделов или объединённый
полный flash-образ. Сервер не доверяет имени файла и проверкам JavaScript.

## Что проверяет устройство

Используется штатная схема **RSA-3072 / RSA-PSS / SHA-256 Secure Boot v2** ESP-IDF
в режиме проверки подписанных обновлений **без аппаратного Secure Boot**.
Вход в веб и подпись независимы: даже администратор не может через этот API
установить неподписанный или подписанный чужим ключом образ.

Подпись подтверждает разрешение владельца закрытого ключа на выпуск образа.
Она не доказывает, из какого Git-репозитория был получен бинарный файл: владелец
ключа должен подписывать только проверенные сборки проекта. Проверка имени проекта
и типа ESP32-S3 дополнительно отсеивает несовместимые файлы, но не заменяет подпись.

`esp_ota_end()` проверяет целостность и подпись по открытому ключу из первого блока
подписи **работающего** образа. Исходный образ, установленный по USB, поэтому тоже
обязательно подписан. Неполная загрузка, неверная подпись, лишние/недостающие данные
не изменяют выбранный загрузочный раздел. Запись идёт блоками до 4 КиБ во внутреннюю
flash; целиком в RAM файл не хранится. Предел ожидания загрузки — 180 секунд,
ожидание очередного сетевого блока ограничено сервером пятью секундами.

Аппаратный Secure Boot, flash encryption и anti-rollback через eFuse не включаются.
USB остаётся доступным для восстановления. Эта защита относится к веб-обновлениям;
физическая перезапись flash и обладатель закрытого ключа находятся за её пределами.
Ранее подписанные версии тоже допускаются. Новый образ может содержать другую
встроенную TLS-пару; ключ подписи OTA и ключ HTTPS — разные ключи.

## Ключ выпуска

- `firmware-signing-public.pem` — открытый ключ проекта, хранится в Git.
- `.signing/ota-key.pem` — закрытый ключ выпуска, **исключён из Git**, права 0600;
  каталог `.signing` — 0700. Не передавать этот ключ с прошивкой или пользователям.
- `tools/prepare_signing.py` сверяет пару при конфигурации и каждой сборке.
  Отсутствующий, открытый для других пользователей или чужой ключ останавливает сборку.
  Ключ не генерируется заново автоматически. `.signing/` нужно резервировать отдельно.

После клонирования проекта восстановить закрытый ключ из своей защищённой копии:

```bash
install -d -m 700 .signing
install -m 600 /private/backup/ota-key.pem .signing/ota-key.pem
python3 tools/prepare_signing.py
bash tools/build.sh
```

Команда `python3 tools/prepare_signing.py --initialize` предназначена только для
первого создания новой идентичности: она отказывает, если уже есть закрытый **или**
открытый ключ. Для существующего проекта восстанавливать ключ, а не заменять его.
Потеря закрытого ключа лишит возможности выпускать обновления для имеющихся плат;
замена доверенного ключа в этой реализации потребует USB-прошивки.

ESP-IDF автоматически подписывает итоговый `build/eth2serial.bin`. Соседний файл
`build/eth2serial-unsigned.bin` — промежуточный, для распространения не предназначен.
Локально в активированной среде ESP-IDF проверить результат можно так:

```bash
espsecure.py verify_signature --version 2 \
  --keyfile firmware-signing-public.pem build/eth2serial.bin
```

## Разметка и первый переход с USB

| Раздел | Адрес | Размер |
| --- | --- | --- |
| NVS | `0x9000` | `0x30000` |
| PHY | `0x39000` | `0x1000` |
| otadata | `0x3a000` | `0x2000` |
| factory | `0x40000` | `0x400000` |
| ota_0 | `0x440000` | `0x400000` |
| ota_1 | `0x840000` | `0x400000` |

Для первоначального перехода нужны новый загрузчик с rollback, таблица разделов,
пустая otadata и подписанное factory-приложение — по адресам из `build/flash_args`.
Предварительно сохранить NVS, старый загрузчик, таблицу и приложение. Полное стирание
flash не требуется. Не менять flash-параметры внутри уже подписанного приложения.
Старый `sdkconfig` может сохранять выключенные параметры подписи: перенести параметры
`CONFIG_SECURE_*` и `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` из `sdkconfig.defaults`
или создать конфигурацию заново из defaults, сохранив свою старую копию.
Сборка явно откажет при отключении обязательных проверок.

После перехода обычное веб-обновление пишет только неактивный OTA-раздел и otadata.
Загрузчик, таблица разделов и factory по вебу не обновляются. Для изменения разметки
или загрузчика понадобится USB. Повторная полная USB-прошивка с `ota_data_initial.bin`
выбирает factory, поэтому не применять её как обычное обновление действующей OTA-платы.

## Проверка запуска и откат

Загрузчик даёт новому образу одну попытку запуска. Прошивка подтверждает себя после
30 секунд стабильной работы Ethernet с адресом, веб-сервера и включённых SSH/Telnet.
Отсутствие microSD и неподключённый serial не мешают проверке. Доступ в интернет не нужен.
Если за 120 секунд службы не готовы, запускается откат. Перезапуск или потеря питания
до подтверждения также возвращают предыдущую прошивку при следующей загрузке.
Отключённый Ethernet или недоступный DHCP в этот период могут вызвать откат исправного
образа. Это проверка запуска служб, а не полная диагностика всех функций.

Веб ждёт новый `boot_id`, нужный OTA-раздел, идентификатор ELF и состояние `valid`.
Сам факт успешной загрузки файла не отображается как успешная установка. По тайм-ауту
или потере связи интерфейс сообщает, что результат не подтверждён; повторять загрузку
следует после проверки состояния устройства.

Обработчик загрузки пока синхронный: во время приёма образа остальные веб-запросы
ждут. Обновление эксклюзивно блокирует serial, операции с картой, сохранение настроек,
новое обновление и сброс кнопкой. Ошибка освобождает блокировку; успех атомарно
переводит её в ожидание перезагрузки.

Источники: [подписанные приложения без аппаратного Secure Boot](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/security/secure-boot-v2.html#signed-app-verification-without-hardware-secure-boot),
[OTA и rollback ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/api-reference/system/ota.html).

## Проверки

`bash tools/test.sh` проверяет блокировки и обращение с ключами;
`tests/ota_web_test.py` — сценарии формы с подменой API. Это не аппаратные испытания.

`tests/ota_device_test.py` использует действующий пароль из приватного локального
файла; пароль не передаётся параметром команды. Тест записывает неактивный раздел,
поэтому его запускать только на подготовленной OTA-плате с резервной копией.
Нужен образ того же приложения, подписанный отдельным тестовым RSA-3072 ключом.
Ключ для такого образа должен отличаться от настоящего ключа выпуска.

```bash
python tests/ota_device_test.py --url http://DEVICE_IP \
  --password-file /private/device-password.txt \
  --foreign-image /private/test/foreign-ota.bin \
  --rollback-test --browser-install
```

Тест проверяет отсутствие доступа без входа, неподписанный и изменённый образы,
чужую подпись, лишние данные, неправильный формат и разрыв загрузки. Параметр
`--rollback-test` дополнительно устанавливает подписанный образ и перезапускает
его до подтверждения, проверяя возврат к прежнему разделу. `--browser-install`
устанавливает образ через настоящий Chromium и ждёт подтверждённого запуска.
Состояние настроек и пользователей сравнивается до и после операций.
Актуальные выполненные испытания — [verification.md](verification.md).
