# esp32_eth2serial_knife

Предварительная прошивка Ethernet → RS-232 для Waveshare ESP32-S3-ETH с PoE-модулем.
ESP-IDF 5.5.5, FreeRTOS, C++20. Прототип прошит на плату; проверены запуск,
DHCP, HTTPS, вход SSH по паролю и перезагрузка через веб с сохранением настроек.
Полный набор аппаратных испытаний ещё предстоит.

## Что входит в версию 0.1

| Возможность | Реализация прототипа |
| --- | --- |
| Ethernet | W5500 по SPI, DHCP / статический IPv4, hostname |
| VLAN | Один 802.1Q VID, 0 = без тега; программное добавление/снятие тега, MTU 1496. Требует проверки на плате |
| SSH | wolfSSH; пароль или публичный ключ OpenSSH; единственный shell-канал к UART, без команд ОС и туннелей |
| Telnet | Пароль, обработка управляющих последовательностей и бинарного IAC; по умолчанию выключен |
| Serial | UART1 GPIO16/17, 1200–115200 бод, 5–8 бит, none/even/odd, 1/2 стоповых бита, без RTS/CTS |
| Владение UART | Одна сессия SSH/Telnet **или** передача файла; веб доступен во время терминальной сессии и передачи |
| Веб | HTTPS, локальные HTML/CSS/JS; состояние, настройки, пользователи, ключи, файлы, система |
| Пользователи | До 8 администраторов; включение/выключение, смена пароля, один публичный ключ на пользователя |
| microSD | FatFS, загрузка и удаление файлов в корне, явное форматирование с повторным монтированием |
| Передача файлов | XMODEM-CRC / XMODEM с контрольной суммой, блоки 128 байт; YMODEM, один файл, блоки 1 КиБ; отмена, тайм-ауты, повторы |
| Почта | SMTP без AUTH и TLS; письмо после загрузки и появления сети, повторы при недоступности сервера |
| Система | Перезагрузка через веб с подтверждением; BOOT 10 секунд и отпускание для заводского сброса |
| Хранение настроек | NVS во внутренней flash; microSD не требуется для настроек, ключей и консоли |

**Пока отсутствуют:** ZMODEM, BREAK, XON/XOFF, передача напрямую с ПК через терминал,
приём файлов от целевого устройства, OTA-обновление самого донгла, SMTP TLS.
ZMODEM остаётся требованием проекта, а не заявленной возможностью этой сборки.
Проприетарное восстановление MikroTik не реализовано.

## Подключение

У экземпляра пользователя нет маркировки ревизии. GPIO выбраны по опубликованной
схеме Waveshare; разводку конкретного MAX3232-переходника ещё нужно проверить.

| ESP32-S3-ETH | TTL-сторона MAX3232 |
| --- | --- |
| GPIO16, UART1 TX | Вход передатчика, T1IN (часто обозначен RX или TXD в зависимости от модуля) |
| GPIO17, UART1 RX | Выход приёмника, R1OUT |
| GND | GND |
| 3V3 | VCC, если модуль рассчитан на питание 3,3 В |

Использовать логические уровни **3,3 В** со стороны ESP32. Выход RS-232 нельзя
подключать непосредственно к GPIO. RS-232-сторона модуля подключается к целевому
устройству подходящим кабелем; прямой или null-modem кабель и назначение контактов
зависят от DTE/DCE и разъёма устройства. RTS/CTS не подключаются.

Подробнее о выводах, PoE и источниках: [docs/hardware.md](docs/hardware.md).

## Сборка

Основной воспроизводимый способ — Docker. Нужны Docker, Git, Bash и доступ к сети
для первого получения образа и библиотек:

```bash
bash tools/build.sh
```

Скрипт проверяет точные коммиты библиотек и собирает в закреплённом образе
`espressif/idf:v5.5.5` с digest. Он не прошивает устройство и не запускает контейнер
с доступом к USB. Зависимости загружаются в игнорируемый каталог `third_party/`.
Изменённые или неверные версии зависимостей приводят к отказу сборки без их перезаписи.

При установленном локально ESP-IDF **v5.5.5**:

```bash
bash tools/dependencies.sh
. /path/to/esp-idf/export.sh
idf.py build
```

Цель ESP32-S3 закреплена в CMake. Получаются:

- `build/eth2serial.bin` — приложение;
- `build/bootloader/bootloader.bin` — загрузчик;
- `build/partition_table/partition-table.bin` — таблица разделов;
- `build/flash_args` — точные адреса и параметры записи, сформированные SDK.

Flash: 16 МиБ, PSRAM: 8 МиБ Octal. Таблица разделов содержит NVS 192 КиБ и
единственный factory-раздел приложения 4 МиБ; OTA-разделов пока нет.
Конфигурация сборки находится в `sdkconfig.defaults`, аппаратные выводы — в
`main/board.hpp`. Менять их перед первым запуском без проверки разводки не нужно.

## Первый запуск

Первый экземпляр прошит 2026-10-11 через Windows COM3 из WSL2.
Результаты — в [отчёте](docs/verification.md), особенности прошивки через Windows —
в [плане испытаний](docs/bringup.md#прошивка-из-wsl2-через-windows).
Следующая инструкция предназначена для новой платы с доступным в ESP-IDF USB-портом.

1. Подключить USB и проверить, что выбран порт именно ESP32-S3-ETH. При необходимости
   войти в загрузчик кнопками BOOT/RESET согласно инструкции Waveshare.
2. В активированной среде ESP-IDF выполнить, заменив порт на фактический:

   ```bash
   idf.py -p /dev/ttyACM0 flash monitor
   ```

   При переходе с другой прошивки сначала сохранить полный дамп и сверить таблицу
   разделов: новая NVS может пересекаться со старыми данными. Первичная очистка NVS
   нужна только при такой миграции; при обновлении нашего прототипа её не стирать.

3. При первом старте без сохранённой конфигурации создаётся пользователь **`admin`**
   с паролем **`admin`**. Эти же данные восстанавливаются после заводского сброса.
   Пароль в USB-консоль не выводится. Обычное обновление прошивки и перезагрузка
   сохраняют уже настроенных пользователей и их пароли.
4. Подключить Ethernet к сети с DHCP. IP виден в USB-логе и списке аренды DHCP.
   Начальные настройки: hostname `serial-dongle`, VLAN выключен, HTTPS 443,
   SSH 22, Telnet выключен, UART 115200 8N1, почта выключена.
5. Открыть `https://<IP>/`. Первый сертификат индивидуальный и самоподписанный;
   браузер запросит решение о доверии. В Chrome: «Дополнительно» → переход на
   устройство. После входа сменить начальный пароль.
6. Настроить serial для целевого устройства, при необходимости сеть и почту.
   Настройки сохраняются сразу, применяются **после перезагрузки**. Пользователи
   применяются сразу; их изменение завершает все веб-сессии. Выключенный пользователь
   теряет активную терминальную сессию при следующей проверке, примерно через секунду.

SSH-подключение: `ssh admin@<IP>`. Публичный ключ `.pub` загружается через раздел
«Пользователи»; приватный пользовательский ключ остаётся на компьютере. Поддержаны
форматы RSA, Ed25519 и ECDSA P-256; конкретные ключи и клиенты нужно проверить на плате.
Для явного выбора ключа: `ssh -o IdentitiesOnly=yes -i /path/to/key admin@<IP>`.

По умолчанию IP резервного статического профиля — `192.168.1.50/24`, шлюз и DNS —
`192.168.1.1`. Он используется только после выключения DHCP, автоматического
перехода на него при отсутствии DHCP нет. Объявления mDNS `.local` пока нет.

Сертификат содержит DNS SAN с hostname на момент создания; при статическом режиме
также добавляется настроенный IP. При DHCP фактический IP в заводской сертификат
не включается. Для входа без предупреждений загрузить доверенный сертификат с SAN,
соответствующим используемому адресу или имени. Смена hostname/IP не перевыпускает
сохранённый сертификат автоматически. Наличие DNS SAN само по себе не создаёт DNS-запись.

Ошибка первоначальной сборки `ERR_CERT_INVALID` исправлена: при обновлении
некорректный заводской сертификат с пустыми расширениями заменяется автоматически,
с сохранением приватного ключа, пользователей и настроек. Корректные импортированные
сертификаты сохраняются. Обычное предупреждение о недоверенной самоподписи остаётся.

## Файлы и обслуживание

Перед передачей загрузить файл на microSD, запустить приём X/YMODEM на целевом
устройстве, закрыть SSH/Telnet и нажать «Передать в serial». Между закрытием консоли
и передачей устройство должно оставаться в режиме ожидания файла. Прототип не
приостанавливает открытую терминальную сессию: занятый UART означает отказ запуска.
Успешная передача означает подтверждение байтов приёмником, не установку прошивки.

Загрузка ограничена 64 МиБ. Имена до 60 ASCII-символов: буквы, цифры, `._-`, без
начальной точки. Веб показывает первые 256 подходящих файлов корня, каталоги не
обходит. Существующий файл необходимо явно удалить перед новой загрузкой.
Оборванная загрузка не публикует частичный файл под конечным именем; служебный
`.upload.tmp` после потери питания удаляется/перезаписывается следующей загрузкой.

Форматирование запускается отдельной задачей только после ввода `FORMAT`. Если
карта не смонтирована, делается явная попытка восстановления файловой системы.
Автоформатирования при старте нет. Успех подтверждается новым монтированием.
Все файловые операции используют общую блокировку карты. Приём файлов через
HTTPS пока синхронный: на время загрузки обработка других веб-запросов задерживается;
UART и отдельные задачи продолжают работать. При форматировании и X/YMODEM веб работает.
После физической замены карты прототип требует перезагрузки; горячая замена не реализована.

Перезагрузка запрещена во время файловой операции, передачи или записи настроек.
После принятия команды новые операции блокируются; рестарт выполняется после
отправки HTTP-ответа. Интерфейс ждёт **новый идентификатор загрузки** устройства.
При изменении IP/VLAN/HTTPS-порта нужно самостоятельно открыть новый адрес.

Заводской сброс: удерживать **BOOT на работающей плате 10 секунд**, дождаться
сообщения готовности в USB-консоли и отпустить. Светодиодная индикация пока не
реализована. Стирается только пространство NVS `knife`: настройки, пользователи,
ключ SSH-сервера и сертификат/ключ HTTPS. Прошивка и microSD сохраняются.
После сброса вход выполняется с `admin` / `admin`; ключи устройства создаются заново. BOOT,
удерживаемая при включении/RESET, включает ROM-загрузчик вместо этого сценария.

## Проверки и ограничения

```bash
bash tools/test.sh
```

Требуются g++ с C++20, ASan/UBSan и Node.js. Проверяются гонка за UART, запрет
рестарта при записи, разбор Telnet, имена файлов, VLAN, CRC, ACK/NAK/повторы,
отмена, тайм-ауты, короткое чтение файла и переход счётчика блоков через 255.

Проверка веба в Chromium с подменённым API:

```bash
python3 -m venv /tmp/knife-web-test
/tmp/knife-web-test/bin/pip install -r tests/requirements.txt
/tmp/knife-web-test/bin/playwright install --with-deps chromium
/tmp/knife-web-test/bin/python tests/web_smoke.py
```

Она проверяет формы, безопасное отображение текста, подтверждение форматирования,
узкий экран и ожидание фактического изменения boot ID. **Этот тест не проверяет
HTTP-обработчики ESP32 или реальную перезагрузку.**

Проверка заводского TLS на доступной плате, с теми же зависимостями Playwright
и установленным Chromium (подставить адрес и hostname своего экземпляра):

```bash
python tests/tls_smoke.py --host 192.168.11.235 --hostname serial-dongle
```

Проверяются DNS SAN и назначение сертификата, затем обычный сценарий Chrome:
предупреждение о самоподписи → явный переход → форма входа и `/api/health`.
Проверка сертификатов Chromium включена; `ignore_https_errors` не используется.
Тест не меняет настройки устройства или системное хранилище доверия.

Аппаратный план проверки — [docs/bringup.md](docs/bringup.md). Пока не подтверждены
PoE, статика/VLAN, совместная нагрузка SSH/HTTPS/microSD и обмен с реальным приёмником.
UART без управления потоком не гарантирует отсутствие потерь при медленном сетевом
клиенте. При потере Ethernet сессия закрывается, повторное подключение — вручную.
Результаты локальных и аппаратных проверок, хеш прошитого образа —
[docs/verification.md](docs/verification.md).

Прототип рассчитан на испытательный стенд: secure boot, flash/NVS encryption и
защита от физического чтения flash ещё не настроены. Пароли хранятся как
PBKDF2-HMAC-SHA256 (индивидуальная соль, 30 000 итераций), ключи — во внутренней NVS.
Криптографический генератор использует включённый внутренний источник энтропии ESP32-S3;
его совместимость нужно пересмотреть при добавлении ADC/I2S/радио.

Версии и лицензии библиотек: [docs/dependencies.md](docs/dependencies.md).
