# Инструкции для агентов

Эти правила действуют для всего репозитория. Явные указания пользователя имеют
приоритет; инструкции во вложенных `AGENTS.md` уточняют правила для своих каталогов.

## Контекст проекта

- Проект: `esp32_eth2serial_knife`.
- Цель: универсальный однопортовый Ethernet → serial донгл с питанием через PoE,
  авторизованным удалённым доступом к консоли и передачей файлов целевому устройству.
- Создан прототип 0.1 на ESP-IDF/C++20; актуальные возможности, ограничения и
  команды проверки находятся в README.md. 2026-10-11 выполнена первая прошивка:
  подтверждены запуск, DHCP, HTTPS, SSH по паролю и перезагрузка через веб
  с сохранением настроек/ключей; подробности — docs/verification.md.
- Подтверждённая плата: Waveshare ESP32-S3-ETH с PoE-модулем Waveshare.
  Планируется преобразователь RS232–TTL на MAX3232; файлы хранятся на microSD.
  Пользователь уточнил: MAX3232 пока не подключён, RTS/CTS отсутствуют, маркировки
  ревизии на плате нет. Для первого подключения рекомендованы TX GPIO16 / RX GPIO17.
  USB и Ethernet подключены; microSD при первом запуске не определяется.
  Serial остаётся физически неподключённым, данные в него при проверках не отправлять.
- По [документации Waveshare](https://docs.waveshare.com/ESP32-S3-ETH):
  Ethernet W5500 через SPI, 16 МБ flash, 8 МБ PSRAM, PoE-модуль IEEE 802.3af.
  16 МБ flash и 8 МБ PSRAM подтверждены на экземпляре. Ревизия кристалла v0.2
  не определяет ревизию PCB, которая по-прежнему неизвестна.
- Первое тестовое устройство: MikroTik CRS125-24G-1S-IN, модель подтверждена пользователем.
- Физическая ревизия платы и модель/разводка MAX3232-переходника пока не установлены.
  Профиль выводов зафиксирован в main/board.hpp по схеме Waveshare; требует проверки.
  В прототипе диапазон UART 1200–115200 бод; расширение требует аппаратных испытаний.
- Не выводи требования из имени репозитория и не переноси аппаратные параметры
  из других проектов без подтверждения их применимости.

## Подтверждённые требования

- SSH: вход по имени/паролю или публичному ключу пользователя, затем доступ к serial.
  Telnet: вход по имени/паролю, затем доступ к тому же serial.
- Serial используется эксклюзивно: одна активная сессия суммарно для SSH и Telnet.
  Второй пользователь может одновременно работать в веб-интерфейсе.
- Все включённые пользователи имеют полные административные права.
  Разделение на роли и режим наблюдателя не требуются.
- Веб-интерфейс: управление пользователями и SSH-ключами, настройками serial,
  IP (DHCP/статика), hostname, одним настраиваемым VLAN ID с тегированием 802.1Q,
  портом веб-сервера, TLS-сертификатами для HTTPS и авторизацией в веб-интерфейсе.
- Файлы загружаются через веб на microSD; донгл отправляет сохранённый файл
  целевому устройству по XMODEM, YMODEM или ZMODEM.
  Прямую передачу файлов с компьютера через терминальную сессию отложить на будущее.
  Приём файлов с целевого устройства пока не согласован.
- Через веб должно быть доступно форматирование microSD для быстрой очистки
  или повторного создания файловой системы при неполадках с картой.
- Через веб должна быть доступна перезагрузка донгла с сохранением его настроек,
  пользователей, ключей/сертификатов и файлов на microSD.
- Не привязывать реализацию передачи файлов к проприетарному восстановлению
  MikroTik. Поддержка протокола приёмником обязательна; отправка файла сама по себе
  не гарантирует установку прошивки. Для испытаний XYZMODEM допустим другой стенд.
- Почта: собственный SMTP-сервер пользователя без авторизации. После загрузки
  и появления сетевой доступности отправлять письмо с IP, hostname, включёнными
  протоколами и портами для подключения, включая веб. Отправитель, получатель
  и параметры сервера настраиваются через веб; режим TLS ещё не определён.
- Все настройки, пользователи и служебные ключи/сертификаты сохраняются во
  внутренней flash независимо от microSD. Отсутствие карты не должно лишать
  устройство настроек и консольного доступа.
- Нужен возврат к стандартным настройкам долгим нажатием кнопки на плате.
- По явному решению пользователя начальные имя и пароль — `admin` / `admin`.
  Они создаются только при отсутствии конфигурации, в том числе после заводского
  сброса. Не выводить пароль в USB-консоль и не заменять существующие пароли
  при обновлении прошивки или обычном запуске.

## Требования к веб-интерфейсу

- Подтверждённые приоритеты пользователя: минимализм, лёгкость отображения
  и высокая скорость загрузки.
- Не использовать декоративные изображения, броские цвета и визуальные эффекты,
  не помогающие управлять устройством.
- Оформление должно быть сдержанным; основное внимание — настройкам, состоянию
  устройства и операциям с файлами.

Предлагаемый подход к реализации; макет и детали ещё не согласованы:

- Простой HTML, небольшой общий CSS и JavaScript только для необходимых действий
  и обновления состояния. Предпочитать стандартные элементы форм и системные шрифты.
- Ресурсы интерфейса хранить во внутренней flash и отдавать с самого устройства,
  чтобы веб работал без интернета и microSD.
- Использовать компактную навигацию, формы и таблицы; сохранять читаемость,
  понятные подписи, видимый фокус клавиатуры и удобство на небольших экранах.
- Цвет использовать умеренно для статусов; ошибки, занятость UART и результат
  операции обозначать также текстом.
- Обновлять изменяющиеся данные без перезагрузки всей страницы и без частого
  опроса неактивных разделов. Размер ресурсов и время загрузки измерить на устройстве.
- В разделе файлов предусмотреть действие «Форматировать microSD» с явным
  подтверждением удаления всех файлов и отображением состояния и результата.
  Форматирование затрагивает только карту; настройки во внутренней flash сохраняются.
- Форматирование требует эксклюзивного доступа к карте: сервер отклоняет запуск
  при активной загрузке, передаче по XYZMODEM или другой файловой операции,
  а во время форматирования блокирует новые операции с картой и повторный запуск.
- Предусмотреть ручное форматирование, когда карта определяется и доступна
  для записи, но её файловая система не монтируется. Ошибка монтирования сама
  по себе не должна запускать форматирование. После операции проверить повторное
  монтирование и показать результат; не обещать исправление аппаратной неисправности.
- В разделе «Система» предусмотреть действие «Перезагрузить устройство», доступное
  после авторизации, с подтверждением и сообщением о разрыве текущих соединений.
- Сервер отклоняет перезагрузку во время передачи по XYZMODEM, загрузки файлов,
  форматирования или записи данных. При принятии команды согласованно блокировать
  запуск новых операций, завершить работу с хранилищами и перезагрузиться после
  ответа веб-клиенту. Не выполнять сброс настроек или форматирование карты.
- На время перезагрузки показывать ожидание восстановления связи; успешный
  запуск подтверждать ответом устройства, а не только истечением таймера.

## Принятый стек прошивки

Решение согласовано с пользователем. Реализация прототипа находится в main/ и components/.

- Основа: нативный ESP-IDF со встроенной FreeRTOS.
- Прикладной код: C++20. Готовые драйверы и библиотеки на C сохраняют свой язык
  и подключаются к приложению через соответствующие API.
- FreeRTOS используется для задач, очередей и синхронизации. Обработка UART
  должна продолжаться независимо от ожидания SMTP и операций веб-интерфейса.
- Веб: HTTPS-сервер ESP-IDF, собственные API и интерфейс управления.
- Хранение: NVS во внутренней flash для настроек и служебных данных;
  FatFS на microSD для загруженных файлов.
- SSH прототипа: wolfSSH v1.6.0-stable + wolfCrypt из wolfSSL v5.9.4-stable.
  ESP-IDF v5.5.5; точные коммиты и digest сборочного образа — docs/dependencies.md.
- Причина выбора: прямой контроль задач, буферов, сетевых служб и владения UART
  при интеграции SSH/Telnet, веб-интерфейса и передачи файлов.
- Версии инструментов закреплены для прототипа. Базовые SSH по паролю и HTTPS
  проверены на плате; microSD, VLAN и остальные сценарии ещё требуют испытаний.
  Не выдавать сборку и модульные/браузерные тесты с подменой API за проверку
  устройства; аппаратный план — docs/bringup.md, результаты — docs/verification.md.
- ZMODEM, BREAK, XON/XOFF и SMTP TLS пока не реализованы. Не удалять их из требований
  из-за ограничений первого прототипа. Светодиодная индикация сброса также отложена.

## Предлагаемые решения и открытые вопросы

Это рекомендации для проектирования, а не утверждение о реализованных функциях.

- Общий механизм владения UART для SSH, Telnet и передачи файла. Во время
  передачи ввод терминала не должен попадать в UART; переход от консоли к
  передаче должен быть явным. Веб-интерфейс остаётся доступным для управления.
- Для универсальности предусмотреть настройки формата UART, аппаратного и
  программного управления потоком и BREAK. Доступность линий и скоростей
  подтвердить по конкретному MAX3232-модулю. RS-232, TTL-UART и RS-485 требуют
  соответствующих электрических интерфейсов.
- Не смешивать публичные ключи пользователей SSH с приватным ключом SSH-сервера
  и приватным ключом HTTPS. Загрузка пользовательских приватных ключей не нужна
  для описанной схемы входа; первоначальную формулировку пользователя уточнить,
  если появится отдельный сценарий их использования.
- Для сброса предлагается удерживать BOOT 10 секунд после запуска прошивки,
  показать готовность индикацией и выполнять сброс с перезагрузкой после
  отпускания кнопки. По [схеме Waveshare](https://files.waveshare.com/wiki/ESP32-S3-ETH/ESP32-S3-ETH-Schematic.pdf)
  BOOT связан с GPIO0; удержание его при аппаратном сбросе может включить
  [ROM-загрузчик](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/advanced-topics/boot-mode-selection.html).
  RESET предназначен для аппаратного сброса; не рассчитывать на измерение
  длительности его удержания работающей прошивкой.
- Предлагаемый заводской сброс очищает конфигурацию и учётные данные донгла,
  сохраняет его прошивку и файлы microSD. В прототипе стирается namespace NVS `knife`,
  включая ключи/сертификаты; стандартный сетевой режим — DHCP без VLAN. При первом
  запуске создаётся admin с согласованным заводским паролем без вывода его через USB.
  Полный набор значений прототипа приведён в README.md; готовность сброса пока
  показывается только в USB-логе, а не светодиодом.
- Работу тегированного VLAN через W5500, размер пакетов и совместную нагрузку
  SSH/HTTPS/microSD проверить на плате до обещаний о полной совместимости.

## Общение и работа с проектом

- Общайся с пользователем и пиши проектную документацию на русском языке,
  если пользователь не попросил иначе. Идентификаторы кода — на английском.
- Перед изменениями изучай существующие файлы и актуальные инструкции.
- Выполняй согласованную задачу до завершения. Рутинные обратимые действия
  выполняй самостоятельно; уточняй отсутствующие данные, влияющие на результат.
- Вноси изменения по задаче, сохраняя пользовательские правки и принятый стиль.
- Не создавай каркас прошивки, зависимости или дополнительные подсистемы
  только ради заполнения пустого репозитория.
- В итоговом сообщении указывай результат, выполненные проверки и существенные
  ограничения. Не выдавай предположения за подтверждённые факты.

## Аппаратная часть

- До выбора драйверов и назначения GPIO установи точную модель и ревизию платы.
  Используй схему, документацию производителя и документацию применяемого SDK.
- Не угадывай распиновку, тип Ethernet-контроллера, интерфейс его подключения,
  объём Flash/PSRAM и параметры питания.
- Для PoE проверь поддерживаемый стандарт или тип питания, состав модуля питания
  и доступный бюджет мощности по документации конкретной платы.
- При подключении периферии проверяй уровни сигналов, занятость выводов,
  ограничения загрузочных GPIO и совместимость с отладкой и интерфейсами платы.
- Подтверждённую распиновку, питание и источники сведений фиксируй в документации
  проекта по мере появления данных; отмечай ревизию платы и непроверенные пункты.

## Прошивка и проверка изменений

- Следуй принятому стеку ESP-IDF/FreeRTOS и C++20; конкретные версии SDK
  и инструментов выбирай с учётом проверенной совместимости зависимостей.
- Фиксируй используемые версии инструментов и зависимостей, а также команды
  сборки, прошивки и просмотра логов в документации после их проверки.
- Держи параметры платы отдельно от прикладной логики. Не размещай пароли,
  ключи, токены и другие секреты в коде, документации или памяти EchoVault.
  Исключение для кода и документации — явно согласованные публичные заводские
  данные входа; пользовательские пароли и ключи под это исключение не попадают.
- Для операций ввода-вывода предусматривай обработку ошибок и тайм-ауты;
  изменения сетевого поведения проверяй также при потере и восстановлении связи.
- Выполняй проверки, соответствующие изменению: сборку и существующие тесты
  для кода, проверку содержания и ссылок для документации. Новые тесты добавляй
  для значимого поведения, а не для повторения реализации.
- При проверке HTTPS отдельно запускать tests/tls_smoke.py с настоящей проверкой
  сертификата Chromium. Успешный вход с ignore_https_errors не подтверждает
  корректность сертификата: так был пропущен ERR_CERT_INVALID в первой сборке.
- Перед прошивкой проверь целевое устройство, порт и параметры сборки.
  Успешная компиляция не подтверждает работу Ethernet, PoE или периферии.
- Если оборудование недоступно, явно укажи, что проверено локально и что
  требует проверки на устройстве. Не заявляй о выполненных аппаратных тестах.

## EchoVault — постоянная память

### Начало работы — обязательно

До планирования, реализации или отладки получи контекст текущей задачи,
если `memory config context` не сообщает `off`:

```bash
memory context --project --agent codex --query "<текущая задача>"
```

Найди относящиеся к задаче записи:

```bash
memory search "<релевантные термины>"
```

Если результат содержит `Details: available`, прочитай подробности:

```bash
memory details <memory-id>
```

Проверяй принадлежность воспоминаний к проекту и актуальность решений.

### Завершение работы — обязательно

Перед завершением задачи, включавшей изменения, отладку, решения или получение
новых знаний, сохрани содержательную запись. Сначала выполни поиск, чтобы
избежать дубликатов. Не включай секреты и учётные данные.

```bash
memory save \
  --title "Краткое название" \
  --what "Что сделано или решено" \
  --why "Причины решения" \
  --impact "Что изменилось" \
  --tags "tag1,tag2,tag3" \
  --category "decision" \
  --related-files "path/to/file1,path/to/file2" \
  --source "codex" \
  --details "Контекст:
Рассмотренные варианты:
Решение:
Компромиссы:
Следующие шаги:"
```

Категории: `decision`, `bug`, `pattern`, `learning`, `context`.
Если EchoVault недоступен, сообщи об этом; не утверждай, что запись сохранена.
